## 1. 目标与首版方向

【已确定】将现有简陋 Agent 窗口升级为符合用户习惯的操作界面，覆盖模型选择、上下文展示与管理、内容添加、权限审批和听写。借鉴 Codex 的交互习惯，具体操作围绕 Vocatrya 的职位、简历和求职数据设计。

【已确定】本地文件加入首版方向；听写仅使用 API，不采用本地转写模型。听写体验参考 Codex，作为本方案的一节维护，不另建独立听写文档。参考交互不代表复用 Codex 内部转写服务，也不承诺与其未公开实现相同。

【建议】复用现有面板与会话管线，先整理已有能力，再接通附件与语音；保持角色、会话、持久化、准入和后端审批兼容。具体排期、阶段边界与开发授权仍待确定。

## 4. D1 模型切换与草稿/附件保留

【源码事实】会话在创建时锁定 connection+model（`chatConversationLock`），锁内连接失效按回合显式报错。已有会话在 `AgentChatIdentity.choose` 中选其他模型 → `startNewConversation({explicit})` → `enterDraft` → `resetTransient`，**当前行为是清空输入草稿、粘贴卡片与上下文条目**；角色槽位草稿（`writeAgentRoleSlot`）只在角色切换时保存文本，不随换模型保留。

【建议】

- 维持「换模型 = 开新会话」契约不变，首版不支持同会话换模型。
- 选择器在会话已锁定状态时明示「将开启新会话」；确认选择后，新草稿**携带当前输入草稿、上下文条目（职位/简历/粘贴文本）与未发送附件卡片**，不清空用户已准备的内容。
- 无可用模型、连接失效、加载失败继续走现有错误横幅（实际原因+设置入口），不静默回退。

【替代方案】

- A. 同会话内换模型：改动锁定契约、历史回放语义与失败边界，首版不建议。
- B. 维持现状全部清空：实现最省，但用户已起草内容随一次误点丢失，不建议。

【影响】`startNewConversation`/`enterDraft` 增加携带参数；粘贴卡片等输入区本地状态需可序列化进槽位快照（现在只存文本）；不动后端锁定与准入。

【待裁定】携带范围是否包含上下文条目与附件（【建议】全部携带）；切换是否加二次确认（【建议】不加模态确认，选择器内文案已说明后果）。

## 5. D2 上下文展示与管理

【源码事实】预算是应用层组装上限（16,000 及分项），估算器为字符密度近似；`buildCareerDialogueContext` 输出 `size`（各分项估算、保留/丢弃回合数），目前只进服务端日志；账户与 Legacy 路径共用同一预算器；`budgets` 参数已支持按调用覆盖。

【建议】

- 工具栏显示「≈x.xk / 16k（估算）」：分子是最近一次服务端实际组装用量，分母是应用预算；两处都标「估算」，不标为模型窗口。
- 点击展开：模型容量（仅当连接元数据提供，否则不显示）、应用预算、当前用量分项（固定开销/历史/显式上下文/工具结果/摘要/当前输入），以及「本次发送丢弃了 N 个较早回合」类裁剪说明。
- 默认自动管理，首版不开放档位或数值配置；当前用户输入、审批与工具结果的保留规则继续由后端执行。

【替代方案】

- A. 精简/标准/扩展档位：依赖会话级持久化与文案，建议列为后续选项而非首版。
- B. 仅接近上限才显示：用户无从理解为何旧消息被裁剪，不建议。
- C. 引入真实 tokenizer：按 provider 增加依赖且与 CJK 估算口径不一致，首版不建议。

【影响】路由需把 `contextSize` 以瞬时 data part 或响应元数据回传客户端；展示逻辑前端为主，不改预算行为。

【待裁定】是否允许会话级预算调节（【建议】首版只读）；裁剪提示是内联在消息区还是仅在展开详情中（【建议】两者都要，内联轻提示+详情解释）。

## 6. D3 首批文件格式、解析与容量

【源码事实】PDF/DOCX 提取管线存在（简历导入口径：≤5 页、≤50,000 字符、30s 超时、zip 炸弹预检）；`PromptInput` 原语已有文件选择/拖放骨架；会话准入当前只放行 `text` 与 `data-paste` part。

【建议】

- 首批格式：`txt`/`md`（直接读文本）、含文本层的 `pdf`、`docx`；走「服务端提取文本 → 注入上下文」路径，与粘贴文本同一类语义。**旧版 `.doc` 不支持**。
- 建议限制（数值为建议起点，裁定后冻结）：单文件 ≤10MB；每条消息 ≤3 个文件；单文件提取文本 ≤50,000 字符，超出截断并标记；提取文本计入上下文预算与当前输入上限。
- 卡片状态：解析中 → 可用（含截断标记）/ 失败（不支持的格式、加密、无文本=扫描件、超限、超时、取消）；失败卡片可移除、不阻塞正文发送，绝不伪报成功。
- 图片、扫描件 OCR、模型原生多模态文件通道**延后**单独评估；提取文字路径与多模态路径分别适配，不因模型名称宣称可用。

【替代方案】

- A. 直接以 FileUIPart/原生文件上传发给模型：绕开提取与预算控制、按 provider 各异、且准入目前拒收，首版不建议。
- B. 首版纳入图片/截图 OCR：无既有 OCR 能力，工作量大且与文字提取路径不同源，建议延后。

【影响】新增上传入口（服务端动作或路由）+ 新 `data-file` 类 part 准入放行；复用 `extract-text` 但限制、错误映射与并发保护按 Agent 场景定义；文件内容视为数据，不授予工具权限。

【待裁定】限制数值最终值；是否同时开放文件选择、拖放与粘贴文件三种方式（【建议】三种，原语已具备）；图片/OCR 是否确认排除首版。

## 7. D4 文件生命周期与外发边界

【建议】

- 发送前：卡片可展开预览**实际提取文本**（含截断位置），用户看到的就是将外发的内容。
- 外发对象：提取文本进入本轮模型请求；不外发原始文件字节、不发送本地路径。
- 保存/重开：提取文本随用户消息持久化（类似 `data-paste` 随会话行保存），重开会话能看到当时发送的内容与标记；**不保存原始文件副本**。
- 删除：发送前移除即彻底丢弃；发送后内容随会话存续，删除会话即一并删除；无本地缓存目录需要清理。
- 敏感边界：只读取用户明确选择的文件，不扩展为目录或任意文件访问；UI 说明哪些内容将发送至当前模型服务。

【替代方案】

- A. 原文件落盘保存以便重开预览原件：引入敏感数据落盘与清理责任，首版不建议。
- B. 只发引用/路径让模型自取：执行面尚无文件权限实现，且暴露本地路径，不建议。
- C. 消费后把提取文本替换为存根（仿 `data-paste` 消费存根）：附件没有等价「消费」语义，首版建议全量保留，若会话体积成问题再议。

【影响】会话 `messages` JSON 体积增长，需要与 `AGENT_CHAT_MAX_STORED_MESSAGES` 等现有限制一并校验；提取文本进入 `contextBudget` 的显式上下文/粘贴类通道。

【待裁定】提取文本在会话中长期保留是否接受（【建议】保留，与粘贴全文现行做法一致）；是否需要对敏感类型（如身份证扫描件命名）做提示（【建议】不做类型猜测，只做外发对象说明）。

## 8. D5 审批展示与策略

【源码事实】`needsApproval` 为逐工具声明；批准绑定持久化准入与执行台账，拒绝不重放、批准不重复执行；卡片已含对象/动作预览与拒绝理由；审批中输入会排队，队列可移除。

【建议】

- 首版**保留既有逐次审批规则**，不新增「全部允许」「本会话不再询问」；不同工具现有审批条件不变。
- 卡片改进：统一显示操作对象、拟执行动作、涉及数据与结果影响；参数可展开；状态文案区分待批准 / 已批准处理中 / 已执行 / 已拒绝 / 失败；批准某次操作不泛化为任意许可的说明保留。

【替代方案】

- A. 会话级允许或全部允许：需要后端授权模型、失效条件与审计语义，建议另立决策，不随展示升级混入。
- B. 只读模式：属于独立产品能力，超出本次范围。

【影响】以前端卡片与状态文案为主；任何新审批模式都必须同步后端校验与持久化语义。

【待裁定】是否接受首版不动审批策略（【建议】接受）；后续扩展审批模式另行裁定。

## 9. D6 API 听写选型

【已确定】使用 API；不下载、不打包、不运行本地转写模型。

【源码事实】BYOK 连接现有 provider：OpenAI、DeepSeek、OpenRouter、Gemini、Ollama（`BYOK_DISPLAY_NAMES`）；凭据经 `credential-store`/`resolveByokCredential` 服务端解密，连接行只存 `credentialRef`；账号登录型（Managed/CLI 运行时）连接没有转写接口面；设置页转写行当前明示无能力。

【核查资料（2026-11-13 查阅）】

| 候选 | 事实 | 来源 |
| --- | --- | --- |
| OpenAI 文件转写 | `POST /v1/audio/transcriptions`；当前推荐模型 `gpt-transcribe`，按分钟计费 $0.0045/分钟；文件 ≤25MB；格式 flac/mp3/mp4/mpeg/mpga/m4a/ogg/wav/webm；支持 `prompt`/`keywords`/`languages` 提示，可做中文与职位术语提示；`whisper-1`、`gpt-4o-transcribe`、`gpt-4o-mini-transcribe`、`gpt-4o-transcribe-diarize` 已弃用，2027-02-26 停服 | developers.openai.com《Speech to text》指南、《gpt-transcribe》模型页与定价页 |
| OpenAI 实时转写 | Realtime API 转写会话（`gpt-live-transcribe` 方向），`gpt-live-1` 定价 $0.05/分钟 | developers.openai.com 定价页 |
| Gemini | 音频可内联（请求总量 <20MB）或经 Files API（免费、单文件 ≤2GB、保存 48 小时）送入对话模型转写，按 token 计费 | ai.google.dev《Audio understanding》《Files API》 |
| DeepSeek | 官方 API 文档仅提供文本类接口，未见音频转写端点 | DeepSeek API 文档（本次查阅未见音频能力） |
| Ollama | 本地服务，与「仅 API、不用本地模型」方向冲突，排除 | — |
| Managed（Codex 等账号登录） | 经 CLI 运行时执行对话，无转写接口；不能假定聊天连接支持转写 | `capabilities.ts` 契约本身不含音频面 |

【建议】

- 转写服务与聊天模型**独立配置**：单独的「听写」设置项 = provider + model + 凭据；更换聊天模型不影响听写，反之亦然。
- 凭据复用已有受保护机制：provider 与已有 BYOK key 相同时复用同一 `ApiKey` 行/解密路径；也允许单独配置听写专用 key。**不能假定现有聊天连接可转写**——Managed 连接天然不可，BYOK OpenAI/Gemini 可复用凭据但配置独立。
- 首版采用「录完再传」的文件转写，不做实时字幕；首选候选 `gpt-transcribe`（专用端点、按分钟计价、支持中文与术语提示），Gemini 音频转写为第二候选。
- 调用前向用户说明音频发送到所选服务；费用按用户自带 key 计费口径在设置中明示。

【替代方案】

- A. 实时流式转写（Realtime/Live）：单价约高一个数量级且复杂度高，建议后续评估。
- B. 产品托管转写（Vocatrya 代付）：涉及费用与额度模型，需用户单独决定商业模式。
- C. 复用聊天连接做转写：Managed 不可行，BYOK 也混淆了「聊天模型选择」与「转写服务」两件事，不建议。

【影响】新增听写设置区块与一条服务端转写路由；复用凭据存储；不引入本地模型。

【待裁定】首版支持的 provider（【建议】OpenAI 先行，Gemini 视实现成本跟进）；BYOK-only 还是允许托管（【建议】BYOK-only 起步）；最长录音时长见 D7。

## 10. D7 听写流程与音频生命周期

【建议】流程：点击麦克风 → 获取权限并开始录音 → 展示录音状态与时长（可复用电平表）→ 可停止或取消 → 停止后显示转写中 → 文字插入发起录音时的草稿（光标处）→ 用户编辑并手动发送。**不自动发送、不覆盖已有输入。**

- 录音上限建议 120 秒硬顶自动停止（听写场景非会议录音；数值待裁定）。
- 音频只存内存：取消即丢弃；转写失败保留音频供一次重试，重试发起或用户放弃后释放；不写磁盘、不入会话数据。
- 迟到/切换保护：录音或转写进行中切换会话或角色时自动停止并按取消处理；转写请求带会话归属，仅未取消且归属仍有效的响应可插入发起草稿；取消或切换后丢弃迟到响应，不串写其他会话。
- 权限拒绝、无设备、设备占用、丢失沿用 `AudioSettings` 的错误分类；转写失败反馈可恢复。
- 退出/关闭面板：麦克风流、MediaRecorder、定时器、临时 Blob 全部释放（沿用现有清理模式）。

【替代方案】

- A. 按住说话：与点击开关并存不冲突，首版建议只做点击开关。
- B. 转写结果另行展示再确认插入：多一步打断，建议直接插入草稿由用户编辑。
- C. 取消后迟到结果仍写回：归属混乱风险，建议丢弃。

【影响】复用 `AudioSettings` 的麦克风生命周期代码需提取为共享逻辑；`AgentChatInput`/Provider 增加录音状态机与插入路径；服务端转写路由见 D6。

【待裁定】时长上限数值；失败重试是否保留音频（【建议】保留一次）；切换会话时迟到结果的处理（【建议】按取消处理并丢弃）。

## 11. D8 布局、无障碍与实施阶段

【建议】同一整体设计（§3 示意），按**独立用户成果**切三个实施包，按共享文件归属串行或显式交接：

| 阶段 | 用户成果 | 主要涉及文件（单一 Owner） | 依赖 |
| --- | --- | --- | --- |
| A 统一输入区 | 输入区整合：添加菜单、模型按钮入工具栏、上下文估算指示、审批卡状态优化；窄面板与键盘/无障碍达标 | `AgentChatInput.tsx`、`AgentChatContextBar.tsx`、`AgentChatIdentity.tsx`、`AgentApprovalCard.tsx`、`AgentChatPanel.tsx`、i18n、`route.ts`（contextSize 回传） | 无前置 |
| B 本地文件 | 选择/拖入/粘贴文件 → 服务端提取 → 卡片预览/状态/移除 → 文本随消息外发并重开可见 | `AgentChatInput.tsx`、新增上传/提取服务端模块、`conversationRequest.ts`（准入）、`contextBudget.ts`（计费通道）、`extract-text.ts`（复用/适配） | A 的卡片行与工具栏 |
| C API 听写 | 设置听写服务（provider/model/凭据）→ 麦克风按钮 → 录音/取消/转写 → 文字入草稿 | `AudioSettings.tsx`（提取共享录音逻辑）、`AgentChatInput.tsx`、新增转写路由与设置存储、i18n | A 的工具栏；B 可与其并行但需输入区文件交接 |

共享文件（输入区组件、Provider、路由、i18n）同一时间只一个 Owner；B 与 C 若并行，输入区组件由 A 的 Owner 统一收口或按文件清单显式交接，避免互改同一文件。

【待裁定】阶段顺序是否调整（【建议】A→B→C，C 依赖 D6 裁定）；是否要求高保真稿；快捷键是否补充（【建议】保持现状 + Esc 取消录音）。

## 12. 决策汇总

| ID | 决策项 | 推荐 | 仍需用户裁定 |
| --- | --- | --- | --- |
| D1 | 模型切换及草稿/附件保留 | 换模型开新会话并携带草稿、上下文与附件 | 携带范围；是否加确认 |
| D2 | 上下文展示与可配置 | 估算用量+分项+裁剪提示；首版只读自动管理 | 是否开放档位；提示位置 |
| D3 | 首批文件 | txt/md/pdf/docx 服务端提取；≤10MB、≤3 个、≤50k 字；OCR/图片延后 | 数值；入口方式；图片确认延后 |
| D4 | 文件生命周期 | 预览即外发内容；文本随消息持久化，不存原件 | 长期保留接受度；敏感提示边界 |
| D5 | 审批 | 保留逐次策略，改进卡片与状态 | 是否接受首版不动策略 |
| D6 | 听写选型 | 独立配置；`gpt-transcribe` 首选；BYOK 凭据复用 | provider 范围；BYOK-only vs 托管 |
| D7 | 听写流程 | 录完再转、插入草稿、不自动发送；音频内存态 | 时长上限；重试保留；迟到归属 |
| D8 | 布局与阶段 | 统一输入区；A→B→C 按用户成果串行 | 阶段顺序；高保真需求；快捷键 |

## 13. 实施顺序与验收

【建议】先完成统一输入区（A），再按授权推进文件（B）与听写（C）；这是依赖顺序，不是新增开发任务授权。配套 JSON 的 `steps` 是待实施验收检查点。最低证据包括：模型选择真实生效且旧会话绑定不变；用量及裁剪与后端组装结果相符；文件内容实际进入请求且失败不伪成功；拒绝审批不执行、批准不重复执行；真实音频 API 返回文字进入正确草稿，取消与失败可恢复。

用户可见路径以隔离数据的 Windows Electron fresh-native 为目标宿主；本轮未执行。开发时按风险选取定向类型/组件/后端检查；需要持久化的功能核对保存与重新打开。完整 E2E、生产构建、安装包或发布另按项目授权规则执行。所有 `passes` 保持 `false`，不能用方案确认、Mock 或代码存在代替功能验收。
