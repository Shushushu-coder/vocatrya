## 1. 目标与首版方向

【已确定】将现有简陋 Agent 窗口升级为符合用户习惯的操作界面，覆盖模型选择、上下文展示与管理、内容添加、权限审批和听写。借鉴 Codex 的交互习惯，具体操作围绕 Vocatrya 的职位、简历和求职数据设计。

【已确定】本地文件加入首版方向；听写仅使用 API，不采用本地转写模型。听写体验参考 Codex，作为本方案的一节维护，不另建独立听写文档。参考交互不代表复用 Codex 内部转写服务，也不承诺与其未公开实现相同。

【建议】复用现有面板与会话管线，先整理已有能力，再接通附件与语音；保持角色、会话、持久化、准入和后端审批兼容。具体排期、阶段边界与开发授权仍待确定。

## 3. 输入区整体设计（AWU-COMPOSER）

【建议】保留现有右侧 Agent 面板、角色入口、历史、新会话及展开能力，统一输入区：

1. 输入框上方展示职位、简历、粘贴文本及本地文件卡片，支持查看、移除和状态提示。
2. 底部工具栏提供「＋ 添加内容」、当前模型、上下文用量、麦克风、发送／停止。
3. 消息区内保留工具执行和审批卡片，状态名称清楚，不把技术参数直接暴露为主要操作。
4. 窄面板下合理折叠工具，键盘、焦点、按钮名称和录音状态可访问。

【待讨论】最终布局、各按钮位置、快捷键及是否需要高保真设计稿；未确定像素级复刻 Codex。

## 4. 模型选择（AWU-MODEL）

【已确定】模型选择属于升级范围。

【建议】输入区显示当前模型和必要连接信息；新草稿直接选择模型，已有会话换模型时明确提示开启新会话，并保留输入草稿。无可用模型、连接失效、加载失败时显示实际原因和设置入口，不静默回退。

【待讨论】模型选择器是否从头部迁移、草稿与附件的跨会话保留规则、是否长期支持同会话换模型。首版建议沿用固定会话绑定。

## 5. 上下文展示与管理（AWU-CONTEXT）

【已确定】上下文大小与管理属于升级范围；具体可配置方式未冻结。

【建议】区分模型容量、应用预算和当前用量；没有实际 tokenizer 数据时标为「估算」。展开可查看携带的职位、简历、文件与历史处理状态；发生裁剪时解释影响，避免让用户误以为全部历史都已发送。

【建议】默认自动管理；精简／扩展档位可作为后续设计选项，不提供超出模型及运行时能力的任意额度。当前用户输入、审批与工具结果的保留规则继续由后端执行。

【待讨论】只展示还是允许调整、档位数值、预算在模型元数据缺失时的处理、会话级设置与持久化、摘要／裁剪提示文案。不得将现有 16k 应用预算写成模型上限。

## 6. 本地文件与内容添加（AWU-FILES）

【已确定】首版纳入本地文件，并统一考虑已有职位、简历和文本内容。

【建议】支持文件选择，拖入及粘贴文件作为交互候选；卡片显示名称、类型、解析中／可用／失败状态，发送前可预览提取内容、移除。文本型 PDF、DOCX、TXT 优先评估本地提取文字后发送；不是授权本地语音模型。提取文字路径与模型原生多模态文件路径分别适配，不因模型名称宣称可用。

【建议】仅读取用户明确选择的文件，不扩展为目录或任意文件访问；展示哪些内容会发送至当前服务。外部文件内容作为数据处理，不授予其工具权限。格式、内容大小、解压和解析限制必须由后端校验；空文本、加密、损坏、超限、取消及格式不支持须有可理解的反馈，不能静默丢弃或假装读取成功。

【待讨论】首批格式清单（旧版 `.doc` 不等于 `.docx`）、扫描 PDF／图片及 OCR、原生多模态支持、单文件与总大小／数量、截断与超预算处理、原文件是否保存、会话恢复所需副本、删除与缓存清理、角色／模型切换后的附件去向。未冻结前不承诺所有模型均可读取所有格式。

## 7. 权限审批（AWU-APPROVAL）

【已确定】改善审批体验，参考 Codex 的清晰操作反馈；具体策略未冻结。

【建议】卡片显示操作对象、拟执行动作、涉及的数据和结果影响，必要时展开详细参数；批准、拒绝、处理中、已执行、失败状态可区分。沿用后端真实授权、幂等和重放边界，批准某次操作不泛化为任意操作许可。

【建议】首版保留既有逐次审批规则；不默认增加「全部允许」。不同工具现有审批条件不同，不将展示升级解释为所有工具都改为需要审批。

【待讨论】是否新增只读／逐次确认／会话允许等模式，允许范围与失效条件，审批中发送消息、关闭面板、刷新恢复的具体交互。若引入新策略，必须一并确定后端校验和持久化语义。

## 8. API 听写（AWU-DICTATION）

【已确定】使用 API；不下载、不打包、不运行本地转写模型。体验参考 Codex 的听写，将语音转换成可编辑输入。

【建议流程】点击麦克风 → 获取权限并开始录音 → 展示录音状态与时长，可取消 → 结束录音 → 显示转写中 → 文字插入当前草稿 → 用户编辑并发送。失败反馈可恢复，不覆盖已有输入、不自动发送。仅有录音或波形不构成转写成功。

【建议】转写服务与聊天模型配置独立；更换聊天模型不要求更换转写模型。音频只在用户主动启动听写后采集，调用前说明发送到所选服务；凭据使用既有受保护机制，不能进入前端暴露、日志或文档。

【待讨论】API 提供商与模型、网络可用性、用户自配凭据还是产品托管、费用与额度、最长录音时长、实时字幕是否需要、草稿插入位置、转写中继续输入或切换会话时的结果归属、取消与重试是否保留临时音频、关闭／退出后的资源清理与数据保留策略。取消后迟到响应不能写入其他会话。

选型依据：OpenAI 官方[转写说明](https://developers.openai.com/api/docs/guides/transcription)与[语音／听写区别](https://learn.chatgpt.com/docs/features/voice)（2026-11-13 查阅）。当日文档推荐录音文件使用 `gpt-transcribe`、实时输入使用 `gpt-live-transcribe`，仅作为候选记录；尚未选定 OpenAI，也未实测质量、费用或中国用户网络条件。Codex 具体内部听写模型未在本轮查阅资料中确认。

## 10. 建议实施顺序与验收

【建议】先完成统一输入区及已有模型／上下文／审批交互，再接通首批文件流程与 API 听写；这是依赖顺序，不是新增开发任务授权。按实际共享文件确定 Owner，不机械按 UI／后端拆分。

配套 JSON 的 `steps` 是待实施验收检查点。最低证据包括：模型选择真实生效且旧会话绑定不变；用量及裁剪与后端相符；文件内容实际进入请求且失败不伪成功；拒绝审批不执行、批准不重复执行；真实音频 API 返回文字进入正确草稿，取消与失败可恢复。
