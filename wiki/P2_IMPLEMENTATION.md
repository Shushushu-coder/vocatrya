## A. P2 目标、范围与台账

### A1. 产品目标

P1 重点是核心业务能力的建立与验收；P2 重点是把职位、简历版本、实际投递、面试题目、面试练习、真实面试复盘、Tasks 与 Agent 连成可理解的求职旅程。

**P2 最优先解决的体验问题**：新用户首次打开软件就知道“准备 → 行动 → 复盘”分别能做什么、从何开始；已有数据的用户能立即看到现阶段重要信息与下一步行动。首页让用户知道：既可以直接使用工作台，也可以主动打开 Vocatrya Agent 辅助操作。

**一条可验收的用户故事**：导入/建立职业素材 → 为目标职位定制并保存简历版本 → 添加职位与记录实际投递及使用的简历版本 → 关联面试轮次和准备题目 → 记录真实面试及复盘 → 在概览看到当前进度、清晰的统计和下一步建议。用户可跳过或返回任意阶段，**不是强制线性向导**。

### A3. 明确不纳入本阶段

- **不做**后台自动 LLM 分析、后台唤醒 Agent、自动多 Agent 协作、AI/搜索推荐算法或静默创建任务。
- **不重新引入** P1 已决定退役的 Activity 计时、休息、时长评分及类似效率打卡体系。
- **不在 P2 重造** P1 的简历解析/模块化拖拽/版本/导出功能，或三种 AI Provider 的连接基础设施；仅在这些能力真实可用时整合入口和业务关联。
- **不扩大**为全功能 CRM、自动发邮件、外部职位搜索平台或完整 Offer 财务比较系统。Notion 求职模板是信息架构参考，而非照搬字段和数据库页面。
- **不将**三个 Agent 等同于三个独立模型、独立进程或自主执行服务；技术形态待审查。

## B. 冻结的首页信息架构

### B1. 首页第一屏与整页组织

首页是**一张可纵向滚动的 Overview 页面**，讲清全部主要业务能力与入口，而不是将每个模块的复杂编辑器塞进同一屏。推荐的阅读顺序：

1. **欢迎与旅程定位**：一句话说明 Vocatrya 如何帮助用户完成“准备 → 行动 → 复盘”；简短呈现当前阶段与可以开始的入口。
2. **三阶段旅程**：准备、行动、复盘各自展示核心工作、对应功能入口和 Agent 辅助入口；阶段可自由跳转，不做强制解锁。
3. **下一步建议**：根据实际业务数据自动推导，直接链接模块，或由用户手动打开对应 Agent；建议不直接调用 AI。
4. **简明数据看板与近期事项**：可信计数、待跟进事项、面试/截止日期等有价值的真实信息；不展示空白或误导性的转化率。
5. **其余核心功能入口**：按三阶段归类，确保用户能从首页理解和进入主要模块；具体密度、卡片组合、桌面与窄屏顺序在界面设计时验证。

可以在不同屏幕宽度重新组织区块，但**不能把三阶段主线藏起来**；一页“呈现全部功能”的含义是主要业务能力**可见且可达**，而不是首页承载所有操作。

### B2. 阶段与 Agent 的稳定对应

| 阶段 | 主要业务故事 | 典型入口 | Agent |
| --- | --- | --- | --- |
| **准备** | 建立与定制简历，理解目标 JD，开展面试准备 | 简历工作台、职位分析、面试题库/练习 | **Voca Insight**（求职分析师） |
| **行动** | 收集/添加职位、记录真实投递、安排与跟进申请 | 机会/职位、投递/流程、Tasks、日历 | **Voca Pilot**（全局助手） |
| **复盘** | 回顾真实面试，沉淀经验并反馈到下一次准备 | 真实面试复盘、历史记录、练习入口 | **Voca Reflect**（复盘教练） |

三个阶段是**产品叙事与常见使用场景**，不是 Agent 独占权限，也不是用户必须依次完成的任务状态机。复盘可以反馈到下一轮准备；在“行动”期间依然可以使用 Insight 准备面试。

### B3. 新用户与已有数据用户

- **新用户/数据很少**：强调完整旅程、简历建立/导入、AI 服务连接（可选增强）、添加职位及第一步操作；统计区域可以使用解释性空态，**不得把示例数字冒充实际记录**。
- **已有业务记录**：保留紧凑的旅程导航，优先呈现下一步建议、临近面试/Deadline、申请进度与统计；不要让固定的大型新手教程持续占据首页。
- **无 AI 配置**：提示进入“设置 → AI 服务”配置，但**不把 AI 连接当作手动使用工作台的前置条件**。
- **有归档数据**：首页与统计如何处理活跃/历史记录须遵守 P1 归档合同，并在 CAREER-INSIGHTS 冻结口径后显示清楚。

## C. 六个 Feature 的产品合同

### C1. JOURNEY-OVERVIEW — 首页讲清求职旅程

**已确认**：统一“准备 → 行动 → 复盘”；一页可滚动地覆盖主要模块入口、进度、数据和 Agent 帮助；每个阶段能进入对应功能，也能手动选择 Agent。新用户和已有数据用户的重点展示不同。

**交互原则**：点击功能卡片进入实际模块；点击 Agent 入口展开右侧聊天面板，**不自动发送消息**。首页应该让用户明白“直接操作”和“让 Agent 辅助”是两种有效选择。与现有导航保持一致，避免重建第二套互相冲突的一级导航。

**验收重点**：首次进入可理解求职主线；主要模块均能到达；已有数据与空态正确；桌面/窄屏可用、Agent 展开不严重压缩主内容；没有不存在的功能入口或伪数据。

**已冻结（2026-11-01，概览合同 §9 D1–D9）**：页面组织、建议上限、dataState 扩展与 Agent 槽位已裁定；实现期仍须先核对真实导航和 P1 交付情况，响应式断点在实施中验证。

### C2. JOB-CONNECTIONS — 职位成为跨模块上下文中心

**已确认的业务关系**：

- 用户可以为目标职位选择**计划使用的简历版本**；这只是准备中的选择，可以调整。
- 某次 `Application Attempt` 的**实际投递简历版本/导出材料**必须保持提交时的真实历史事实。不能因为后来修改了简历版本，就把历史投递内容一起改掉。
- 同一职位可能存在多次申请、不同流程节点和多轮真实面试；面试题目、练习与真实复盘需要能找到对应上下文。
- 职位详情可以聚合相关信息，但尽量复用已有 Job Opportunity、Application Attempt、Resume Version、面试题目/练习与业务服务，不复制完整实体。

**建议的用户体验**：从职位详情可看到“目标简历版本”“投递记录与实际提交版本”“面试轮次与准备内容”“真实面试复盘”几个关联视角；对尚无关联的部分提供清楚的建立入口。关联操作须可见、可更正，并且不能隐式改写历史事实。

**已冻结（2026-11-01，联合合同 §13 D1–D12）**：复用 `JobOpportunity → ApplicationAttempt → ProcessStep → InterviewDetail` 现有树，提交快照不可变、题目挂轮次级复盘（快照+可空回链）、归档/删除/备份语义均已裁定；Schema 变更仅限裁定的 additive 增量。

**验收重点**：同一职位多次申请、一个申请多轮面试、简历新版本不覆盖既往提交、题目复用、归档恢复后关联仍完整，且不会产生跨用户数据泄露。

### C3. INTERVIEW-DEBRIEF — 真实面试复盘

**已确认**：真实面试复盘与“模拟面试练习”是不同业务记录。支持逐轮复盘并连接职位/申请/面试轮次；可以引用已有题库/练习，也可以记录真实面试中出现的新问题。复盘可沉淀下一次练习或改进建议，但不应强制使用 AI。

**已冻结（2026-11-01，联合合同 §13 D1–D12）**：复盘内容＝`reflectionText` 自由文本 + 逐题 `{questionText, answerNotes}` + 显式 `reflectionCompletedAt` 完成标记；发生时间复用 `scheduledAt`/`completedAt` 两列；复盘不驱动申请状态。

**体验边界**：用户可以手动记录和查看全部复盘；建议/问题若转成 Task 应经用户操作确认。Voca Reflect 可在用户主动请求后辅助整理总结，但 AI 总结不可无提示地覆盖用户原始叙述，也不能把推测自动写成事实。

**验收重点**：一个职位多轮独立复盘、关联题目和练习、记录可读可编辑、无 AI 时正常工作、AI 辅助与原始记录区别清楚，并验证权限与历史读取。

### C4. NEXT-ACTIONS — 数据驱动、确定性规则推荐下一步

**冻结原则**：系统读取业务数据后自动生成引导，**规则计算不调用 LLM，也不搜索/推荐外部职位**。建议只引导用户进入功能模块或主动打开对应 Agent，不自动创建任务、不自动投递、不自动执行 Agent。

| 已知业务状态 | 首页应该给出的下一步 | 执行性质 |
| --- | --- | --- |
| 没有简历或可用职业素材 | 前往简历模块导入或建立素材 | 普通模块导航 |
| 没有配置可用 AI 服务 | 前往 AI 服务设置；告知 AI 是可选辅助 | 普通模块导航 |
| 尚无职位或尚未开始实际投递 | 引导添加/导入目标职位并准备投递 | 普通模块导航 |
| 有职位但缺少针对目标岗位的简历版本 | 前往模块化简历工作台选择或建立版本 | 普通模块导航 |
| 有即将发生的真实面试 | 进入关联题目和面试准备入口 | 普通模块导航 |
| 有已结束、尚未复盘的真实面试 | 开始真实面试复盘，并可进入后续练习 | 普通模块导航 |

前四条中“无简历、未配置 AI、未投递”的业务状态及“真实面试完成后建议复盘”由 Owner 明确提出；其余候选规则作为**基于已确认旅程的建议**，需在功能设计时核对真实数据可判定性。不能把模拟练习“完成”误判为真实面试“已结束”。

**已冻结（2026-11-01，概览合同 §9 D1–D9）**：候选规则、3 条上限、无 dismiss、「已结束」＝仅 COMPLETED、AI 可用按 `CAREER_DIALOGUE` 存储态、分家族投递口径、R3 按未归档职位判定等均已裁定。

**验收重点**：新账号、无 AI、有职位未投递、结束真实面试未复盘、多状态同时成立、用户归档/恢复、数据变化后的同步刷新。不得因打开首页产生 AI 调用或业务写入。

### C5. CAREER-INSIGHTS — 清楚且可信的数据看板

专项口径、源码核查与 Owner 交接见 [统计合同](./P2_CAREER_INSIGHTS_CONTRACT_PROPOSAL.md)，已于 2026-11-01 裁定冻结（§8 D1–D9）。

**已确认**：使用少量高价值指标辅助决策，避免复杂的评分墙。候选基础指标包括职位数、实际投递次数/申请数、面试相关机会、Offer、待跟进事项；漏斗与转化率在定义清楚后再交付。

**必须先明确的统计合同**：

- **计数单位**：职位、一次申请、一次面试轮次分别是什么；一个职位多次投递或多轮面试如何去重。
- **转化率**：分子/分母与统计窗口是什么，不能将面试轮次数直接除以职位数。
- **当前与历史**：归档职位的历史申请是否仍计入累计数据、筛选是否会改变口径，必须清楚标注。
- **零/缺失数据**：样本不足、未知状态、零分母用“暂无/不适用”表达，不以 0% 冒充有效分析。

**验收重点**：多次申请、多轮面试、Offer 状态、归档数据、零分母与日期筛选的指标数值一致；不恢复 Activity 时长/计时、无依据的效率评分或 AI 自动职业评估。

### C6. MULTI-AGENT — 三个专业化 Agent 与右侧面板

**冻结的角色与用户故事**：

| Agent | 旅程定位 | 负责的场景 | 技术边界 |
| --- | --- | --- | --- |
| **Voca Insight** · 求职分析师 | 准备 | 简历、JD、职位匹配与面试准备的深度分析 | 基于已授权且实际可用的简历/匹配/题目工具；freshNativeFull 下 canonical `match_job` 已接通且 P1 记录真实 AI/Electron 验收通过，结论限于实际覆盖运行时/模型；三角色能力仍须按白名单与运行时交集核实 |
| **Voca Pilot** · 全局助手 | 行动 | 检索与管理工作台、添加职位、经确认的操作 | 复用当前已可用工具与写入确认边界；不自动实际投递 |
| **Voca Reflect** · 复盘教练 | 复盘 | 整理真实面试经历，提炼经验与改进方向 | 只有在复盘数据/工具真实支持时才提供对应可执行建议 |

**冻结的右侧 Agent 面板交互**：

1. 用户从首页阶段卡片、功能页面入口或现有 Agent 入口**主动打开右侧面板**；不因打开首页自动运行 AI。
2. **Agent 切换位于面板顶部**，仅放三个图标，鼠标 hover 显示名称；图标应有键盘焦点/辅助功能名称。**不得在面板左边添加占据聊天宽度的 Agent 选择栏**。
3. 面板中显示当前 Agent 名称、职责简介与 **4 条建议**。建议必须与已实现工具/业务能力匹配；不能把待规划工具写成已可执行提示。
4. 点击建议**只填入输入框**，用户仍可编辑；只有用户确认发送才执行 AI。已有发送、取消、工具批准/错误处理机制须尊重实际运行时契约。
5. 从具体职位、简历或面试进入时，可附带**明确且可见的当前对象上下文**；从首页直接打开时不凭空选择目标。面板跨页面可保留，但页面、对象、Agent 切换时要展示/清除过期上下文，防止误操作。
6. 阶段入口只是默认推荐，用户在任何阶段均可手动切换任一 Agent。三个 Agent **不要求**三个独立模型，不允许后台自主协作或定时分析。

**已有 P1 边界须保留**：P1 记录的 fresh-native/full 工具现为 `list_jobs`、`get_job`、`add_job`、`get_resume`、`review_resume`、canonical `match_job`（恒需批准；P1 记录实际路径验收通过）。独立 canonical FAST_SCREENING/MatchAnalysisService 必须继续作为复用业务能力。三个 Agent 的每个工具是否可用、具体 Provider 下是否支持相关运行方式、是否允许写入，**均必须按新阶段的真实代码与业务验证收敛**。不能因设置三个角色就默认新增能力已经存在。

专项推荐与决策表见 [MULTI-AGENT 合同](./P2_MULTI_AGENT_CONTRACT_PROPOSAL.md)，目前均为提案。

**已冻结（2026-11-01，多 Agent 合同 §9 D1–D10）**：每角色独立会话槽、`agentRole` 列、统一 `CAREER_DIALOGUE` 锁、白名单矩阵、建议填入不发送、面板尺寸与降级形态已裁定；仍不得先决定任意跨 Agent 历史共享或跨用户数据访问。

**验收重点**：顶部图标和 hover 名称、实际聊天宽度、四条建议点击填入但不发送、三 Agent 手动切换、清晰的对象上下文、跨页面防误用、无连接态、读取权限和所有写入批准边界；打开首页或打开 Agent 面板本身不触发 AI 请求。

| P2 工作 | 上游依赖 | 设计/实施约束 |
